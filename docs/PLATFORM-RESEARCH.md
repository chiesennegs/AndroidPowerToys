# Android 17 access decisions

Researched 2026-10-30 against Android developer documentation, the installed Android 17 API 37.0 revision 2 SDK source, and the `android17-release` SettingsProvider source. Original application code and artwork are maintained in this project.

- [Settings.System](https://developer.android.com/reference/android/provider/Settings.System#canWrite(android.content.Context)): `WRITE_SETTINGS` plus explicit special-app-access approval. Detect with `Settings.System.canWrite`; this is not a runtime permission dialog.
- [Android 17 manifest](https://android.googlesource.com/platform/frameworks/base/+/android17-release/core/res/AndroidManifest.xml): `WRITE_SECURE_SETTINGS` retains `signature|privileged|development|role|installer`. Development permissions may be explicitly granted by ADB. This app declares it and verifies its actual state. Manual commands are copy-only; optional wireless setup executes a fixed grant/revoke only after explicit confirmation. Device policy/build restrictions can refuse it. No target-SDK downgrade or root is used.
- [Android 17 SettingsProvider](https://android.googlesource.com/platform/frameworks/base/+/android17-release/packages/SettingsProvider/src/com/android/providers/settings/SettingsProvider.java): `getAllSystemSettings`, `getAllSecureSettings`, and `getAllGlobalSettings` filter keys using `enforceSettingReadable`. `@Readable` and maximum target SDK limits still apply to ordinary applications; holding WRITE_SECURE_SETTINGS does not make an app a system app. Additional permission checks and redaction can apply. Enumeration is always a visible subset. Exact reads can throw; these are never converted into absence.
- `enforceRestrictedSystemSettingsMutationForCallingPackage` limits ordinary apps to public System keys / ringtone keys for insertion and update, rejects deletion of platform-defined System keys, and rejects arbitrary additions at a modern target SDK. ADB granting WRITE_SECURE_SETTINGS does not make the caller shell or privileged. Android PowerToys exposes these limitations and blocks unsupported System operations locally. Secure/Global mutations enforce WRITE_SECURE_SETTINGS and may still fail user restrictions, validators, special permissions or ownership rules.
- Normal `ContentResolver.query/insert/delete` uses `Settings.*.CONTENT_URI`. Direct query counts preserve absent versus present-null/empty/zero; direct CRUD avoids the typed convenience API's null/absence ambiguity and migrated-key forwarding. An accepted insert/delete alone is insufficient: a second exact query must match. Verification is immediate provider-exposed state, not proof that a consuming service applied the setting or that it will persist forever.
- System/Secure generally use the calling Android user; Global uses the system user's global state. No cross-user API, user picker, profile traversal or cross-user permission is included.
- [Settings.java, Android 17](https://android.googlesource.com/platform/frameworks/base/+/android17-release/core/java/android/provider/Settings.java): both content-filter flags are annotated readable. Positive values enable filtering; non-positive values disable the signal. The app uses literal documented key names because these constants are hidden SDK APIs. No hidden API invocation is needed. These keys retain generic filtering descriptions in the tables; the dedicated diagnostic and incident example were removed in v1.5.
- [AGP 9.2 release notes](https://developer.android.com/build/releases/agp-9-2-0-release-notes): supports API 37.0, Gradle 9.4.1 and Build Tools 36.0.0. The project uses 9.2.1 with built-in Kotlin 2.2.10 and the matching Compose compiler plugin.

Snapshots contain coverage labels and per-table errors. Comparison rejects different user serial identifiers, coverage or unreadable tables. It compares the two files' visible rows; it cannot detect changes in omitted/redacted rows. A user serial is not a device identity: compare files only from the same device. Files are limited to 8 MiB, parsed as versioned JSON with duplicate-row/state validation, and never applied to the device. Capture is sequential, not an atomic OS-wide transaction.

History uses app-private `noBackupFilesDir` and `AtomicFile`, with a durable PENDING entry before each write. A crash can leave PENDING; a read-back failure leaves UNVERIFIED. Neither is represented as success. Undo records another change, checks the current state still equals the prior target, and never overwrites a conflicting newer value. This is an optimistic check, not a cross-process compare-and-swap: another process can race between the check and write. Write verification can also observe redacted values; the UI explains provider-exposed visibility.
