# Secure/Global access without ADB or wireless debugging

Researched 2026-10-30. User clarified that both ADB and wireless debugging are excluded. The original no-root requirement remains. No device debugging commands, permission grants, settings writes or app changes were performed for this investigation.

## Result

No supported general-purpose route was found for an ordinary, newly installed Android PowerToys APK to edit arbitrary Secure/Global rows on a stock, non-rooted Pixel under these constraints. A normal user permission prompt does not grant WRITE_SECURE_SETTINGS. Keep those tables read-only unless permission was already legitimately granted; supported public System edits can still use normal Modify system settings approval.

## Paths evaluated

- **WRITE_SECURE_SETTINGS**: Android 17 declares `signature|privileged|development|role|installer`, not a dangerous/runtime permission. Merely requesting it, adding an accessibility service, or being a conventional device administrator does not meet those grants. [Android 17 manifest](https://android.googlesource.com/platform/frameworks/base/+/android17-release/core/res/AndroidManifest.xml), [permission reference](https://developer.android.com/reference/android/Manifest.permission#WRITE_SECURE_SETTINGS).
- **Device/profile-owner APIs**: `setSecureSetting` supports a short allowlist such as DEFAULT_INPUT_METHOD and SKIP_FIRST_USE_HINTS; modern location changes have a dedicated API. `setGlobalSetting` also supports a limited list. These do not provide arbitrary table edits and do not list the browser/search content-filter flags. Device-owner enrollment is a separate management/provisioning relationship, not a standard permission dialog for this utility. [setSecureSetting](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setSecureSetting(android.content.ComponentName,%20java.lang.String,%20java.lang.String)), [setGlobalSetting](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setGlobalSetting(android.content.ComponentName,%20java.lang.String,%20java.lang.String)).
- **Privileged roles**: the Android 17 DEVICE_POLICY_MANAGEMENT role includes WRITE_SECURE_SETTINGS, but is static, invisible, configured by the platform, and has dedicated provisioning components. It is not a user-selectable utility-app permission. Do not claim that becoming an ordinary device admin, default browser or assistant grants it. [Android 17 role configuration](https://android.googlesource.com/platform/packages/modules/Permission/+/refs/heads/android17-release/PermissionController/res/xml/roles.xml).
- **New Settings Preference APIs**: WRITE_SYSTEM_PREFERENCES can control preferences exposed by host settings services, rather than arbitrary raw rows. The service also requires READ_SYSTEM_PREFERENCES, protected by signature/privileged/role grants. AOSP's special-access list explicitly hides apps without the read grant, explaining that it requires pre-grant or role. Therefore declaring the new write permission does not create a general approval path for this app. [Permission reference](https://developer.android.com/reference/android/Manifest.permission#WRITE_SYSTEM_PREFERENCES), [special-access eligibility source](https://android.googlesource.com/platform/packages/apps/Settings/+/9e67fd6d317e9a7f680e2920d0175d2b25ddf679/src/com/android/settings/spa/app/specialaccess/WriteSystemPreferences.kt), installed API 37 SettingsPreferenceService/Client source.
- **Native Android settings screens**: users can change settings exposed by the privileged Settings app, subject to the screen's own authorization. Linking to those screens is a valid narrower approach; it is not arbitrary key/value editing, and some raw rows have no corresponding user-facing control. The SDK includes a flagged supervision-settings action, but its existence is not proof that a particular Pixel build exposes controls for these exact two filtering flags or that a stale flag can be corrected there. No verified control for those exact raw filtering keys was established.

No exploits, root setup, bootloader changes, factory reset, managed provisioning, silent elevation, or automated interactions with permission screens were attempted. Research does not establish an exhaustive impossibility theorem about every OEM extension; the conclusion is scoped to supported APIs available to this ordinary app on the specified stock-device configuration.
